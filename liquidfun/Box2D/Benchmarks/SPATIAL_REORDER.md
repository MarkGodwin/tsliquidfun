# Per-substep particle spatial reordering experiment

Baseline checkpoint: `95346ed4` (shared proxy scratch committed before this work).
Disposition: rejected after desktop measurements; experimental code, temporary
API/Testbed switch and experiment-only regression tests were removed. The cached
position in each proxy, fused classification and shared proxy-sort scratch were
retained. This document records the discarded implementation and its results.

## Discarded implementation

The existing global proxy sort was retained. During its final merge, a separate
concrete merge loop assigned the next destination index in each group/range,
gathered positions and emitted proxies with their new indices. There was no extra
comparison sort of particles, per-particle virtual call or template sorter.
One branch per merge selected ordinary versus reordered output.

Group ranges remained unchanged, including retained empty groups. Each contiguous
ungrouped run was treated as a separate range. A reusable position-sized staging
buffer then gathered the remaining persistent attribute arrays and copied them
back, preserving addresses of engine-owned and externally supplied buffers.
The group-pointer array was unchanged; temporary accumulation arrays were
regenerated by the solver. Three reusable integer arrays held range starts,
write cursors and the old-to-new map. Additional scratch capacity was 20 bytes
per slot on the tested builds, plus the existing 8-byte proxy sort scratch. Storage
grew geometrically and was reused after warmup.

Handles, lifetime indices, old particle/body contacts and stuck-particle lists
were remapped. Spring/barrier pairs and elastic triads were remapped by vertex
slot, preserving their reference geometry. Constraint buffers were sorted by
their remapped keys using allocation-free std::sort. Constraints were not
recreated. Reordering occurred only during Solve contact updates, once per
particle substep; group construction/join/split contact updates did not reorder.

The temporary API was SetSpatialReorderingEnabled(bool), default false. Testbed
applied its Spatial Particle Order checkbox to all systems. Raw indices changed
every substep, requiring handles to retain identities. User-supplied buffer
addresses were preserved. Neither the API nor the checkbox is retained.

## Separate correctness issues discovered

Listener regression uncovered two pre-existing contact-set lookup bugs: the
LightweightPair comparator used component-wise AND instead of lexicographic
ordering, and lower_bound was accepted without checking key equality. The
experiment corrected both so remapped old contacts produced correct
begin/end events, also with reordering disabled. It also remapped stuck-particle
index lists during group rotation and zombie compaction to prevent stale indices
from entering the reorder pass. These fixes were reverted with the experiment;
they are recorded here as candidates for separate fixes and regression tests.

## Validation

Before removal, 264 tests across 14 executables passed in Release and Debug;
Debug enabled detailed profiling and shadow proxy validation. Added checks
covered identity preservation
for persistent attributes, handles/lifetimes, external buffers, group ranges,
old contacts and stuck lists, exact constraint vertex/reference preservation,
constraint buffer ordering, listener continuity, water trajectory comparison,
join/split/deletion/expiry, elastic/spring evolution and barrier confinement.
No simulation baselines were changed. Native Testbed and benchmark builds passed;
the on/off checkbox and paused timing overlay were visually verified, with
evidence at benchmark-results/spatial-reorder/testbed.png. Historical key-only
replay and a world matrix run with --reorder on also passed;
JavaScript/iOS toolchains and the target Pi are unavailable here.

Benchmark steering uses stable identities for teleport and deletion, and final
hashes cover positions, velocities and flags in identity order. Six-scene smoke
runs and all 36 paired measured runs had bit-identical on/off hashes. Profiled
runs had identical per-frame contacts, body contacts, candidates and processed
particle counts, with zero scratch growth after warmup.

## Desktop measurements

Same MSVC x64 Release executable, instrumentation and shadow validation disabled.
Six scenes, 3000/5000 particles, two particle iterations, 200 warmup steps and
600 measured steps. Three alternating off/on process pairs per case; figures
are medians of the three per-run medians. Positive percentage means less time.
All copying, remapping and sorting is inside measured physics time. Benchmark
particles carry identity in userData in both modes; moving that optional
attribute is included in the reorder cost. This is an
initial implementation that preserves buffer addresses through copy-back;
results do not establish a limit for designs using owned double buffers.

Separate detailed builds (two alternating pairs, 5000 particles) show proxy
stage cost rising by approximately 0.08-0.09 ms/frame. Preparation/copy/remap
accounts for 0.07-0.08 ms/frame. Contact discovery and the remaining solver show
little consistent improvement. This desktop experiment therefore does not pay
back its cost. Target-Pi behaviour still needs measurement.

Generated raw data and scripts: benchmark-results/spatial-reorder/. The clean
measurements.csv retains median, mean, p95, p99 and max; profile.csv holds stage
means. An archived experimental Testbed executable, saved benchmark executables and
source.patch (the discarded tracked-source diff against the baseline) are also
in that ignored local directory. These generated artifacts are not committed;
the findings and method above are the durable record.

## Interpretation

The extra movement and index bookkeeping outweighed the locality benefit in
these scenes. This experiment does not justify reordering particle storage on
every substep. A design that exchanges owned destination buffers instead of
copying attributes back could have different costs; no such design was measured.
Pi Zero W behaviour remains unknown.

In the profiled 5000-particle runs, the remaining solver took about 0.57-0.68 ms
per frame, contact discovery about 0.35-0.51 ms and the original proxy stage
about 0.025-0.053 ms. Thus much of the time was already outside proxy sorting.
Further solver work need not begin with changing equations: measuring specific
passes, eliminating repeated calculations and improving their data access are
possible directions, but this experiment establishes no speedup for them.

After removing the experiment, the retained cached-proxy implementation was
rebuilt: all 258 tests across 14 executables passed in both Release and Debug,
and the Testbed Release build succeeded. The normal comparison/new Testbed
copy was refreshed with this retained implementation.
